# 第 1 章 产品概述

## 1.1 产品定位

### 一句话定义

> **一款数字分身交付工具**（Windows 桌面应用），让 ToB 用户通过六阶段向导式流程，复刻"Barry 数字分身"的完整制作链路——从知识萃取、知识组织、人格塑造、交互设计，到部署交付、持续演化——即开即用地交付属于自己的 AI 数字分身。工具本身不内置任何业务内容，仅提供方法论产品化的通用能力。

### 核心命题

> **不是做一个具体的 Barry 数字分身，而是把"制作 Barry 数字分身的方法论"产品化为一款工具。**
>
> 用户使用本工具，等同于跟随一位经验丰富的"数字分身制作教练"，按六阶段法完成自己的数字分身交付。工具承担方法论中所有可工程化的环节（向量化、检索、硬规则、阶段分类、信号检测），用户只负责提供原始资料和业务判断。

### 产品形态

| 维度 | 说明 |
|------|------|
| **交付形态** | Windows 桌面安装包（.exe，PyInstaller onedir 模式） |
| **运行方式** | 本地运行，数据本地存储（SQLite + ChromaDB） |
| **接入方式** | 通过 HTTP/RPC 远程对接用户已运行的 WCF（WeChatFerry）实例，工具本身不内置 WCF |
| **AI 能力** | 接入用户自备的 LLM API（DeepSeek / OpenAI 兼容协议） |
| **核心能力** | 六阶段向导 + 知识萃取 + LLM Wiki + 人设编辑器 + 硬规则 + 阶段分类器 + 信号检测 + 六层消息处理引擎 + WCF 远程对接 + 消息监控 + 双模式交互 |
| **业务内容** | 工具不预设任何业务逻辑，所有业务内容由用户通过六阶段向导自定义 |

### 双模式设计要点（延续 v2.0）

| 模式 | 面向场景 | 交互方式 |
|------|---------|---------|
| **Agent 对话模式** | 偏好自然语言交互、希望快速完成的用户 | 类似 TRAE / Cursor 的对话窗口，用户描述需求，Agent 调用工具完成配置、查询、操作 |
| **传统工具模式** | 偏好可视化表单、需要批量配置的用户 | 配置页、表单、下拉选项、按钮，所见即所得 |

两种模式共享同一份配置数据，可随时切换，上下文保留。**六阶段向导作为第三种顶层入口**，引导用户按顺序完成数字分身制作；用户也可跳过向导，直接通过双模式独立操作任意阶段。

## 1.2 目标用户

### 主要用户画像

| 用户类型 | 典型场景 | 核心需求 | 付费意愿 | 优先级 |
|---------|---------|---------|---------|--------|
| **内容创作者 / KOL** | 把自己的项目经验、内容资产提炼为可对外服务的数字分身 | 知识萃取向导、双用途知识条目、人设塑造工具 | 高（数字分身即产品） | P0 |
| **ToB 私域运营团队** | 为品牌搭建可复用的 AI 客服 / 数字分身 | 标准化交付流程、可复制的方法论、零代码配置 | 高（团队效率） | P0 |
| **CPS 玩家 / 个人创业者** | 微信群内推广电商优惠、佣金变现 | 自定义导购话术、自动回复、商品推荐规则 | 中（省人力成本） | P0 |
| **电商客服团队** | 微信私域承接售前咨询、售后处理 | 自定义 FAQ、订单查询逻辑、转人工规则 | 中（提效） | P1 |
| **知识付费 / 教育机构** | 课程咨询、答疑、引流到课 | 自定义知识库、答疑 Prompt、线索收集 | 高（客单价高） | P1 |
| **品牌方 / 大客户** | 品牌客服、会员服务、统一话术 | 多账号管理、品牌素材库、合规审核 | 高（要求私有化） | P1 |

### 用户能力假设

| 能力维度 | 假设 |
|---------|------|
| **技术能力** | 不需要懂代码，能看懂界面操作；Agent 模式下能用自然语言描述需求 |
| **方法论认知** | 不需要预先了解六阶段方法论，工具向导会逐步引导 |
| **微信环境** | 用户自行在另一台电脑上配置好 WCF + 微信 + 绕过检测工具，并启动 WCF HTTP/RPC 服务 |
| **LLM 配置** | 用户能自行申请 DeepSeek / OpenAI API Key |
| **业务配置** | 用户能自行梳理业务话术、FAQ、知识库内容；工具不提供任何业务模板作为默认值 |

## 1.3 核心价值主张

### 对用户的价值

> **"你不需要懂代码，也不需要从零摸索数字分身怎么做。打开工具，按六阶段向导走一遍，把你的项目资料、人设偏好、业务规则填进去，就能交付一个属于你的 AI 数字分身。工具承担方法论的工程化，你只需做业务判断。"**

### 价值拆解

| 价值点 | 说明 |
|--------|------|
| **方法论产品化** | 把"Barry 数字分身制作方法论"固化为六阶段向导，用户即开即用，不需重新摸索 |
| **知识萃取自动化** | 五步蒸馏法（盘点→分类→提炼→入库→验证）产品化为向导，降低用户提炼知识的门槛 |
| **LLM Wiki 治理** | 三层架构（Schema/Wiki/Raw Sources）+ ChromaDB 混合检索，让知识库可维护、可扩展、可溯源 |
| **硬规则可配置** | 250 字截断、问句结尾、步骤限制、术语解释等硬规则可视化配置，代码层强制执行 |
| **零成本阶段分类** | 本地关键词匹配替代 LLM 意图分类，<1ms 响应、零 API 成本 |
| **六层消息引擎透明** | 信号检测→阶段分类→向量检索→会话历史→Prompt 组装→LLM 调用，每一步可观测、可调试 |
| **双模式交互** | Agent 对话模式让小白用户也能用自然语言完成配置；传统工具模式让老手高效批量操作 |
| **远程对接** | WCF 与业务物理隔离，用户自行管理微信环境，工具只做合规的远程调用 |
| **数据本地化** | 所有配置和对话数据本地存储，用户完全掌握数据主权 |

## 1.4 产品边界

### 做什么

| 能力域 | 说明 |
|--------|------|
| 六阶段向导 | 提供知识萃取→知识组织→人格塑造→交互设计→部署交付→持续演化的向导式流程 |
| 知识萃取 | 支持多源资料导入、五步蒸馏向导、双用途知识条目编辑、Embedding 模型配置 |
| 知识组织 | LLM Wiki 三层架构、index.md 自动维护、双向链接、Lint 健康检查、ChromaDB 混合检索 |
| 人格塑造 | 七段结构人设编辑器、硬规则配置器、控制变量法调试器 |
| 交互设计 | 阶段分类器配置、信号检测器配置、六层消息处理引擎、Fallback 策略 |
| 部署交付 | WCF 远程对接、LLM 配置、部署前自检、测试发送 |
| 持续演化 | 纠错记录收集、反馈闭环、知识库版本管理 |
| 双模式交互 | Agent 对话模式 + 传统工具模式 + 模式切换 |
| 消息监控 | 实时展示收发消息流、处理结果、异常告警 |

### 不做什么

| 不做什么 | 原因 |
|---------|------|
| **不内置 WCF 运行时** | 合规隔离要求；WCF 由用户自行在另一台电脑部署 |
| **不提供 WCF 安装教程** | 不在官方文档教用户安装 WCF 和绕过检测工具 |
| **不预设业务模板** | 所有业务内容由用户通过六阶段向导自定义 |
| **不内置意图分类规则** | 阶段分类器由用户配置关键词字典，工具不预置业务阶段 |
| **不预设 CPS 平台配置** | 不预置好单库 / 美团 / 淘宝等平台 API，用户按需自行接入 |
| **不做公众号 / 视频号接入** | MVP 阶段聚焦微信个人号 |
| **不做图片 / 视频生成** | 仅处理文本对话与已有素材转发 |
| **不分发 WCF 和版本绕过工具** | 合规红线 |
| **不替用户做业务判断** | 工具承担工程化，业务内容由用户决策 |

## 1.5 合规策略

### 三不原则（延续 v2.0）

| 原则 | 具体做法 |
|------|---------|
| **不提微信 Hook** | 官方文档和宣传中使用"AI 数字分身""数字分身交付工具"等概念，不强调"微信机器人""Hook" |
| **不内置 WCF** | 工具核心框架不含 WCF 运行时代码，仅通过 HTTP/RPC 远程对接用户独立部署的 WCF 实例 |
| **不提供安装教程** | 不在官方文档教用户安装 WCF 和绕过工具，由用户自行解决 |

### WCF / WS 物理拆分的安全边界（延续 v2.0）

| 层级 | 部署位置 | 责任方 | 内容 |
|------|---------|--------|------|
| **WCF 层（WS 端）** | 用户自行管理的另一台电脑 | 用户 | WCF 运行时 + 微信 + 绕过检测工具 + HTTP/RPC 服务端 |
| **业务层（本工具）** | 用户本地电脑 | 用户 | AI Bridge 桌面应用，仅通过 HTTP/RPC 调用 WCF 层 |
| **合规边界** | 网络隔离 | — | 工具代码仓库不含 WCF 源码、不含绕过工具、不含安装教程；仅包含 HTTP/RPC 客户端调用代码 |

### 法规对标

| 法规 | 对标措施 |
|------|---------|
| 《互联网信息服务深度合成管理规定》 | WCF 层与业务层物理隔离，工具不分发深度合成相关工具链 |
| 《生成式人工智能服务管理暂行办法》 | LLM 调用由用户自备 API，工具不提供模型服务；用户对生成内容负责 |
| 《人工智能生成合成内容标识办法》 | 工具在生成消息中保留可配置的标识字段（由用户决定是否启用） |

## 1.6 与 v2.0 的关键差异

| 维度 | v2.0 | v3.0 | 变更原因 |
|------|------|------|---------|
| **产品定位** | 通用型 AI 客服 / AI 数字分身管理系统 | 数字分身交付工具 | 聚焦"交付"动作，让 ToB 用户即开即用复刻方法论 |
| **用户旅程** | 三步引导（WCF→LLM→测试发送） | 六阶段向导（知识萃取→知识组织→人格塑造→交互设计→部署交付→持续演化） | 把方法论产品化为用户旅程 |
| **知识库** | 通用文档导入 + 切片 + 向量检索 | LLM Wiki 三层架构 + ChromaDB 混合检索 + 双向链接 + Lint | 引入治理能力，支持长期演化 |
| **知识条目** | 单一用途（给 AI 检索） | 双用途（技术层给 AI 检索 + 内容层给公域内容生产） | 一份知识两用，降低用户维护成本 |
| **人设配置** | 通用 Prompt 编辑器 | 七段结构人设编辑器 + 硬规则配置器 + 控制变量法调试器 | 把人设方法论产品化 |
| **意图识别** | LLM 意图分类（8 类通用意图） | 本地关键词阶段分类器（零成本 <1ms） + LLM FC（复杂场景） | 成本控制 + 响应速度 |
| **消息处理** | 简单的 LLM 调用链 | 六层消息处理引擎（信号检测→阶段分类→向量检索→会话历史→Prompt 组装→LLM 调用） | 方法论工程化 |
| **信号检测** | 无 | proceed/repeat/stuck/chat 四信号检测 | 支持教学/服务场景的状态机 |
| **硬规则** | 无 | 250 字截断、问句结尾、步骤限制、术语解释，代码层强制执行 | 微信阅读习惯 + 教学场景 |
| **WCF 对接** | 远程对接（保留） | 远程对接（保留，作为阶段五的支撑） | 不变 |
| **双模式交互** | Agent 对话 + 传统工具 | Agent 对话 + 传统工具 + 六阶段向导（第三种入口） | 新增向导作为顶层导航 |

## 2.1 功能清单总览

### 六阶段模块化清单（v3.0）

| 阶段 | 模块 | 功能 | MVP |

### 2.2.2 五步蒸馏向导

**功能目的**：把"五步蒸馏法"产品化为引导式向导，降低用户提炼知识的门槛。

**五步流程**：

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  Step 1      │    │  Step 2      │    │  Step 3      │    │  Step 4      │    │  Step 5      │
│  盘点资产    │ ─→│  设计分类    │ ─→│  逐条提炼   │ ─→│  向量化入库 │ ─→│  检索验证   │
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
```

| 步骤 | 用户操作 | 工具动作 |
|------|---------|---------|
| **Step 1 盘点资产** | 浏览导入的原始资料，确认资产范围 | 展示资产清单，按类型分组统计 |
| **Step 2 设计分类** | 创建 5-8 个知识分类（按用户视角而非技术架构） | 提供分类模板参考（公众号接入/AI引擎/部署运维/踩坑经验/案例场景/工具资源/方法论/架构感知） |
| **Step 3 逐条提炼** | 为每条知识填写：标题、分类、核心要点（3-5条）、解决方案、注意事项、来源文件 | 提供双用途条目编辑器（技术层+内容层）；LLM 辅助提炼（可选） |
| **Step 4 向量化入库** | 确认 Embedding 模型配置，点击"开始入库" | 调用 bge-small-zh-v1.5 生成向量，存入 ChromaDB，更新 wiki/index.md |
| **Step 5 检索验证** | 输入 10-20 个典型问题，查看 Top-K 检索结果 | 展示相似度分数、命中条目；若 Top-1 相似度 < 45% 给出优化建议 |

## 2.3 阶段二：知识组织模块

### 2.3.1 LLM Wiki 三层架构

**功能目的**：把"散落的珍珠"串成"项链"，让知识库可维护、可扩展、可溯源。

**三层架构**：

```
┌─────────────────────────────────────────────┐
│  Schema 层（kb_schema.md）                    │
│  定义规则：页面类型、工作流、命名规范          │
│  所有权：用户与 LLM 共同演化                  │
└───────────────────┬─────────────────────────┘
                    │ 约束
┌───────────────────▼─────────────────────────┐
│  Wiki 层（知识库 MD 文件）                     │
│  结构化知识条目：技术层 + 内容层               │
│  所有权：LLM 维护写入，用户可审查修正          │
└───────────────────▲─────────────────────────┘
                    │ 编译（Ingest）
┌───────────────────┴─────────────────────────┐
│  Raw Sources 层（原始资料）                    │
│  项目代码、对话记录、纠错记录、运营数据         │
│  所有权：用户所有，LLM 只读不改                │
└─────────────────────────────────────────────┘
          + 辅助检索
┌─────────────────────────────────────────────┐
│  ChromaDB 向量检索（混合架构辅助层）           │
│  bge-small-zh-v1.5 + 512维向量               │
│  作用：Wiki 索引定位的补充搜索                 │
└─────────────────────────────────────────────┘
```

### 2.3.2 index.md 自动维护

**功能目的**：知识库索引自动维护，用户无需手动同步。

| 项 | 说明 |
|---|---|
| **触发时机** | 新增条目、更新条目、删除条目时自动同步 |
| **索引维度** | 1) 按分类索引；2) 按学习阶段索引；3) 按页面类型索引 |
| **索引字段** | KB-ID、标题、页面类型、学习阶段、来源文件 |
| **统计摘要** | 条目总数、分类数、阶段数、页面类型数、孤儿条目数 |

### 2.3.3 双向链接管理

**功能目的**：建立知识条目间的关联，支持溯源和导航。

| 项 | 说明 |
|---|---|
| **链接格式** | `[[KB-XX-XXX]]` |
| **链接位置** | 1) frontmatter 的 `related` 字段；2) 正文中的自然引用 |
| **链接规则** | 1) 必须指向存在的条目；2) 自动建立反向链接；3) 删除条目前检查入站链接 |
| **孤儿检测** | 标记没有入站链接的条目（不阻断，仅提示） |

### 2.3.4 Lint 健康检查（🔜）

**功能目的**：定期检查知识库健康度，防止"Drift"（静默过时）。

| 检查项 | 说明 | 严重度 |
|--------|------|--------|
| 矛盾检测 | 不同条目对同一概念的描述矛盾 | 高 |
| 过时检测 | 被新条目取代的旧观点未标记 | 高 |
| 孤儿页面 | 没有入站链接的 KB 条目 | 中 |
| 缺失页面 | 被引用但不存在的 `[[KB-XX-XXX]]` | 高 |
| 缺失交叉引用 | 语义相关但没有互链的条目 | 低 |
| Stage 映射缺失 | 新增条目未在阶段分类器中注册 | 中 |
| Frontmatter 不完整 | 缺少必填字段的条目 | 中 |
| 知识缺口 | 重要概念被提及但无专页 | 低 |

### 2.3.5 ChromaDB 混合检索

**功能目的**：Wiki 索引定位 + 向量语义补充的混合检索。

**混合查询流程**：

```
查询请求
  │
  ├─→ 1. 读 wiki/index.md（快速定位，零成本）
  │      └→ 找到候选条目列表
  │
  ├─→ 2. ChromaDB 向量检索（语义补充）
  │      └→ top_k=5，按 stage 过滤
  │
  ├─→ 3. 合并去重
  │      └→ Wiki 定位 + 向量检索的并集
  │
  └─→ 4. 注入 Prompt
         └→ 最多 2 条知识，避免超长
```

**查询成本对比**：

| 方式 | 耗时 | 成本 | 准确率 |
|------|------|------|--------|
| 仅读 index.md | <1ms | 零 | 中（依赖索引完整性） |
| ChromaDB 向量检索 | ~50ms | 低 | 高（语义匹配） |
| 混合查询 | ~50ms | 低 | 最高 |

## 2.5 阶段四：交互设计模块

### 2.5.1 阶段分类器

**功能目的**：用本地关键词匹配实现零成本、<1ms 响应的阶段分类，替代 LLM 意图分类。

**核心机制**：

| 项 | 说明 |
|---|---|
| **分类方式** | 本地关键词字典匹配（零 API 成本） |
| **响应时间** | <1ms |
| **阶段定义** | 用户自定义 `stage_0` ~ `stage_N`，每个阶段对应一组关键词 |
| **关键词字典** | 用户在配置界面维护，支持正则 |
| **Fallback** | 无命中时归为默认阶段（如 `stage_chat`） |

**阶段分类器配置示例**（参考方法论的 10 阶段）：

| 阶段 | 关键词示例 | 说明 |
|------|-----------|------|
| `stage_0` | 摸底、诊断、了解 | 第 0 课-摸底诊断 |
| `stage_1` | 准备、开始、第一步 | 第 1 课-准备工作 |
| `stage_2` | 公众号、配置、Token | 第 2 课-公众号配置 |
| `stage_3` | 服务器、部署、环境 | 第 3 课-服务器环境 |
| `stage_4` | 大模型、DeepSeek、API | 第 4 课-接入大模型 |
| `stage_5` | 人设、Prompt、风格 | 第 5 课-设计人设 |
| `stage_6` | 知识库、RAG、向量 | 第 6 课-搭建知识库 |
| `stage_7` | 微信、消息、接入 | 第 7 课-接入微信消息 |
| `stage_8` | 测试、上线、验证 | 第 8 课-测试上线 |
| `stage_9` | 迭代、优化、反馈 | 第 9 课-持续迭代 |
| `stage_chat` | （默认） | 闲聊/兜底 |

**与知识库联动**：每个阶段对应一组 KB 条目（stage_kb_map），检索时按当前阶段过滤，只返回当前阶段相关知识。

### 2.5.2 信号检测器

**功能目的**：识别用户消息中的"信号"，决定消息处理引擎的下一步动作。

**四种信号**：

| 信号 | 触发关键词 | 引擎动作 |
|------|-----------|---------|
| `proceed` | 继续、下一个、下一步、OK | 推进到下一阶段/下一知识点 |
| `repeat` | 重复、再说一遍、没听懂 | 重复当前知识点，换一种说法 |
| `stuck` | 卡住、不会、怎么办 | 提供更详细的解释或回退到上一阶段 |
| `chat` | （默认） | 普通对话，按当前阶段处理 |

**配置项**：

| 项 | 说明 |
|---|---|
| 信号关键词字典 | 用户自定义每个信号的关键词列表 |
| 信号优先级 | 多信号命中时的优先级（默认 stuck > repeat > proceed > chat） |
| 信号与阶段的联动 | 不同阶段下同一信号的不同处理逻辑 |

### 2.5.3 六层消息处理引擎

**功能目的**：把方法论的"六层交互引擎"产品化为可观测、可调试的消息处理链路。

**六层流程**：

```
用户消息
   │
   ▼
┌─────────────────────────────────────────┐
│  Layer 1: 信号检测                       │
│  - 本地关键词匹配                        │
│  - 输出：proceed/repeat/stuck/chat       │
│  - 耗时：<1ms                            │
└─────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────┐
│  Layer 2: 阶段分类                       │
│  - 本地关键词字典                        │
│  - 输出：stage_0 ~ stage_N               │
│  - 耗时：<1ms                            │
└─────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────┐
│  Layer 3: 向量检索                       │
│  - ChromaDB 混合检索                     │
│  - 按 stage 过滤                         │
│  - 输出：Top-K 知识条目                  │
│  - 耗时：~50ms                           │
└─────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────┐
│  Layer 4: 会话历史                       │
│  - 从 SQLite 加载会话上下文              │
│  - 输出：最近 N 轮对话                   │
│  - 耗时：<5ms                            │
└─────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────┐
│  Layer 5: Prompt 组装                    │
│  - 人设 Prompt + 检索结果 + 会话历史     │
│  - 变量插值                              │
│  - 输出：完整 Prompt                     │
│  - 耗时：<1ms                            │
└─────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────┐
│  Layer 6: LLM 调用                       │
│  - 调用 DeepSeek/OpenAI API              │
│  - 硬规则后处理（字数截断、问句结尾）    │
│  - 输出：最终回复                        │
│  - 耗时：1-3s                            │
└─────────────────────────────────────────┘
   │
   ▼
最终回复
```

**可观测性**：每一步的输入、输出、耗时记录到消息监控面板，便于调试。

### 2.5.4 Fallback 策略

**功能目的**：处理检索失败、LLM 超时、限流等异常情况。

| 异常场景 | Fallback 策略 |
|---------|--------------|
| 检索无结果（Top-1 相似度 < 阈值） | 使用人设 Prompt 直接生成（不注入知识） |
| ChromaDB 不可用 | 降级为仅读 index.md 定位 |
| LLM 调用超时（>15s） | 返回占位语"稍等，我查一下"，异步重试 |
| LLM 限流（429） | 排队等待，3 次失败后告警 |
| LLM API Key 无效 | 立即告警，停止处理 |
| 硬规则触发截断 | 截断后追加"...（回复字数超限，已截断，如需完整回复请说'继续'）" |

## 2.6 阶段五：部署交付模块

### 2.6.1 WCF 远程对接（延续 v2.0）

**功能目的**：通过 HTTP/RPC 接口对接用户已运行的 WCF 实例，实现消息收发与微信账号管理。

| 项 | 说明 |
|---|---|
| **输入** | WCF 实例的 IP、端口、Token（可选） |
| **输出** | 连接状态、消息流、发送结果 |
| **处理流程** | 1) 用户在配置页填写 WCF 实例地址 → 2) 工具发起 HTTP/RPC 握手请求 → 3) WCF 返回微信账号信息（昵称、wxid） → 4) 工具建立长连接订阅消息推送 → 5) 收到消息后进入六层消息处理引擎 |
| **异常处理** | 连接失败时给出具体原因（网络不通 / 端口未开放 / Token 错误）；断连后自动重连，3 次失败后告警 |
| **合规约束** | 工具仅包含 HTTP/RPC 客户端代码，不包含 WCF 服务端代码；连接配置不持久化 Token 明文 |

### 2.6.2 LLM 配置（延续 v2.0）

| 项 | 说明 |
|---|---|
| **输入** | API Key、Base URL、模型名、温度、Prompt、上下文消息列表 |
| **输出** | LLM 响应文本、Token 用量、耗时 |
| **处理流程** | 1) 用户在配置页填写 LLM 凭证 → 2) 工具发起测试请求验证连通性 → 3) 业务流程中按场景组装 Prompt → 4) 调用 chat completion 接口（支持流式） → 5) 返回结果并记录 Token 消耗 |
| **异常处理** | API Key 无效、配额超限、网络超时分别给出明确提示 |
| **合规约束** | API Key 本地加密存储，不上传任何外部服务 |
| **DeepSeek 端点** | `https://api.deepseek.com/chat/completions`（非 OpenAI 格式，注意路径无 `/v1` 前缀） |

### 2.6.3 部署前自检

**功能目的**：在正式部署前，检查配置完整性，避免运行时故障。

**自检项**：

| 检查项 | 通过条件 |
|--------|---------|
| WCF 连接 | 握手成功，返回合法微信账号 |
| LLM 连通性 | 测试请求收到合法响应 |
| 知识库 | 至少 1 条知识条目已入库 |
| 人设 Prompt | 至少 1 个人设已配置 |
| 阶段分类器 | 至少 1 个阶段已配置关键词 |
| 信号检测器 | 4 个信号均已配置关键词 |
| 硬规则 | 字数截断、问句结尾已启用 |
| Fallback 策略 | 至少配置了"检索无结果"和"LLM 超时"的兜底 |

### 2.6.4 测试发送

**功能目的**：选择联系人发送测试消息，验证完整链路。

| 项 | 说明 |
|---|---|
| **前置条件** | 部署前自检全部通过 |
| **用户操作** | 选择测试联系人（或输入 wxid），输入测试消息，点击发送 |
| **工具动作** | 调用六层消息处理引擎生成回复 → 通过 WCF 发送给联系人 → 展示发送结果 |
| **通过条件** | 联系人收到消息（用户在微信端确认） |
| **失败处理** | 区分 WCF 发送失败、LLM 调用失败、硬规则触发，给出具体提示 |

## 3.1 六阶段向导主流程

**核心创新**：把方法论的六阶段产品化为用户旅程，用户按顺序走完六阶段，即完成数字分身交付。每个阶段采用**任务流引导模式**，包含"目标→任务清单→产物→验证→下一步"闭环。

│ ✅任务   │ ✅任务   │ ✅任务   │ ✅任务   │ ✅任务   │ ✅任务   │

| **可回退** | 用户可回退到上一阶段修改 |
| **进度持久化** | 向导进度持久化到本地，重启后恢复 |

## 3.4 阶段间衔接机制

### 衔接检查

| 衔接 | 检查项 | 不满足时的处理 |

### 数据传递

| 衔接 | 数据传递 |
|------|---------|
| 阶段一→二 | 知识条目 → wiki/index.md + ChromaDB |

### 4.5.3 交互规范

| 交互 | 操作 | 效果 |
|------|------|------|
| 点击节点 | 鼠标左键单击 | 弹出条目详情卡片（标题/分类/摘要/操作按钮） |
| 双击节点 | 鼠标左键双击 | 跳转到条目编辑页面 |
| 拖拽节点 | 鼠标左键拖拽 | 手动调整布局（力导向自动回弹） |
| 缩放 | 鼠标滚轮 | 缩放图谱 |
| 点击连线 | 鼠标左键单击 | 高亮双向链接的两个节点 |
| 搜索 | 输入关键词 | 高亮匹配的节点，其他节点变灰 |
| 按分类过滤 | 下拉选择分类 | 只显示该分类的节点 |
| 按状态过滤 | 下拉选择状态 | 只显示该状态的节点 |

### 4.5.4 数据来源

| 数据项 | 来源 |
|--------|------|
| 节点 | LLMWikiManager.list_all() 的 entry_id + title + category + status |
| 连线 | DualPurposeEntry.related 字段（双向链接） |
| 节点大小 | 该条目在其他条目的 related 字段中被引用的次数 |
| 节点颜色 | category 字段映射 |

### 4.5.5 技术实现

| 项 | 说明 |
|------|------|
| 渲染引擎 | PyQt6 QGraphicsView + 自定义力导向布局 |
| 力导向算法 | 简化版：斥力（所有节点相互排斥）+ 引力（有链接的节点相互吸引）+ 阻尼（防止无限加速） |
| 性能优化 | 节点数 < 100 时实时渲染；> 100 时启用渐进加载 |

### 5.3.2 Ingest 工作流

```
1. 读取原始资料 → 放入 data/raw_sources/（只读）
2. LLM 提炼关键信息 → 按 KB 标准格式撰写条目
3. 判断页面类型（concept/procedure/pitfall/case/methodology/decision/overview）
4. 检查是否需要新建页面还是更新已有页面
5. 创建/更新 KB 条目 → 添加到 data/wiki/entries/
6. 更新 data/wiki/index.md（追加条目到索引）
7. 更新 data/wiki/log.md（追加操作记录）
8. 更新 frontmatter（kb_entries 列表）
9. 更新 stage_classifier.py 的 stage_kb_map（如涉及新阶段）
10. 运行 build_vector_kb.py 重建向量库
11. 运行 build_vector_kb.py --test 验证检索效果
```

### 5.3.3 Query 工作流（混合查询）

```
1. 先查 wiki/index.md（快速定位，零成本）
2. 如果 index 定位不足 → 调用 ChromaDB 向量检索（语义补充）
3. 合并结果，去重
4. Stage Classifier 过滤（只保留当前学习阶段相关知识）
5. 注入 Prompt 生成回复
```

## 5.4 阶段分类器与信号检测实现

### 5.4.1 阶段分类器实现

```python
# 伪代码示例
class StageClassifier:
    def __init__(self, stage_keywords: dict):
        """stage_keywords: {"stage_0": ["摸底", "诊断", "了解"], ...}"""
        self.stage_keywords = stage_keywords

    def classify(self, user_input: str) -> str:
        """返回命中的阶段，无命中返回 stage_chat"""
        for stage, keywords in self.stage_keywords.items():
            for kw in keywords:
                if kw in user_input:
                    return stage
        return "stage_chat"
```

**关键特性**：
- 零 API 成本（纯本地匹配）
- <1ms 响应
- 支持正则表达式
- 用户可在配置界面维护关键词字典

### 5.4.2 信号检测器实现

```python
# 伪代码示例
class SignalDetector:
    SIGNAL_KEYWORDS = {
        "proceed": ["继续", "下一个", "下一步", "OK", "好的"],
        "repeat": ["重复", "再说一遍", "没听懂"],
        "stuck": ["卡住", "不会", "怎么办"],
    }
    PRIORITY = ["stuck", "repeat", "proceed", "chat"]

    def detect(self, user_input: str) -> str:
        """返回命中的信号，无命中返回 chat"""
        hits = []
        for signal, keywords in self.SIGNAL_KEYWORDS.items():
            for kw in keywords:
                if kw in user_input:
                    hits.append(signal)
                    break
        if not hits:
            return "chat"
        # 按优先级返回
        for signal in self.PRIORITY:
            if signal in hits:
                return signal
```

## 5.5 硬规则执行机制

### 5.5.1 硬规则 vs 软规则

| 类型 | 执行层 | 可绕过 | 示例 |
|------|--------|--------|------|
| **硬规则** | 代码层 | 否 | 字数截断、问句结尾、步骤限制、术语解释 |
| **软规则** | Prompt 层 | 是（LLM 可能不遵守） | emoji 使用、链接格式、语气风格 |

### 5.5.2 硬规则执行器实现

```python
# 伪代码示例
class HardRulesExecutor:
    def __init__(self, config: dict):
        self.config = config  # {"max_chars": 250, "force_question": True, ...}

    def apply(self, llm_output: str) -> str:
        """对 LLM 输出应用硬规则"""
        result = llm_output

        # 1. 字数截断
        if self.config.get("max_chars"):
            max_chars = self.config["max_chars"]
            if len(result) > max_chars:
                result = result[:max_chars] + "...（回复字数超限，已截断，如需完整回复请说'继续'）"

        # 2. 问句结尾
        if self.config.get("force_question"):
            if not result.rstrip().endswith(("？", "?")):
                result += "\n\n请问这个解释清楚了吗？"

        # 3. 步骤限制（通过 Prompt 层控制，代码层只校验）
        # 4. 术语解释（通过 Prompt 层控制，代码层只校验）

        return result
```

| **工具实现** | 五步蒸馏向导 Step 2 提供分类模板参考（公众号接入/AI引擎/部署运维/踩坑经验/案例场景/工具资源/方法论/架构感知） |
| **来源** | KB-07-002 |

### 6.2.3 决策3：零成本阶段分类 → 本地关键词匹配

| 项 | 说明 |
|---|---|
| **方法论决策** | 不使用 LLM 做意图分类（成本高、延迟高），改用本地关键词匹配（零成本、<1ms） |
| **工具实现** | 阶段分类器使用本地字典 + 正则匹配，配置界面让用户维护关键词 |
| **来源** | 方法论一、1.3 + KB-07-008 |

### 6.2.4 决策4：硬规则代码层强制 → 硬规则执行器

| 项 | 说明 |
|---|---|
| **方法论决策** | 250字截断、问句结尾、步骤限制、术语解释必须由代码层强制执行，不能依赖 Prompt（LLM 可能不遵守） |
| **工具实现** | 硬规则执行器在 Layer 6（LLM 调用）之后对输出做后处理：字数截断、追加问句 |
| **来源** | 方法论一、1.3 |

### 6.2.5 决策5：LLM Wiki + ChromaDB 混合 → 混合检索

| 项 | 说明 |
|---|---|
| **方法论决策** | LLM Wiki 为主（知识编译+索引），ChromaDB 为辅（语义搜索补充）；规模 < 50 条时 Wiki 索引够用，规模 > 几百条时向量检索价值显现 |
| **工具实现** | 混合查询流程：先读 index.md 定位 → 再 ChromaDB 语义补充 → 合并去重 → stage 过滤 |
| **来源** | KB-09-001、KB-09-004 |

## 6.3 双用途知识条目设计

### 6.3.1 设计原则

> 一份知识两用：技术层给 AI 检索（精炼、关键词密集），内容层给公域内容生产（完整、有案例）。

### 6.3.2 字段对照

| 用途 | 字段 | 给谁用 | 设计原则 |
|------|------|--------|---------|
| **技术层** | `search_text` | AI 检索 | 精炼、关键词密集、去掉代码块噪音 |
| **技术层** | `metadata`（category/stage/tags/related） | ChromaDB 过滤 | 结构化、可枚举 |
| **内容层** | `content_body` | 公域内容生产 | 完整、有案例、可读性强 |
| **内容层** | `summary` | index.md 导航 | 一句话摘要 |

### 6.3.3 工具支持

- 知识条目编辑器提供"技术层"和"内容层"两个独立编辑区
- LLM 辅助提炼：从 content_body 自动生成 search_text 草稿
- 公域内容导出：从 content_body 一键导出为公众号推文/视频脚本草稿

## 6.4 零成本阶段分类的工程化

### 6.4.1 为什么不用 LLM 做意图分类

| 维度 | LLM 意图分类 | 本地关键词匹配 |
|------|------------|--------------|
| 成本 | 每次调用 ~0.001 元 | 零 |
| 延迟 | 200-500ms | <1ms |
| 准确率 | 90%+ | 80%+（依赖关键词字典质量） |
| 可调试 | 黑盒 | 白盒，可追踪命中关键词 |

### 6.4.2 工具实现的关键点

1. **关键词字典用户可维护**：配置界面让用户随时增删关键词
2. **支持正则表达式**：应对复杂的匹配场景
3. **Fallback 机制**：无命中归为默认阶段（stage_chat）
4. **与知识库联动**：每个阶段对应一组 KB 条目，检索时按阶段过滤
5. **可观测**：消息监控面板展示命中关键词和分类结果

## 6.5 硬规则 vs 软规则的边界

### 6.5.1 划分原则

| 类型 | 划分原则 | 示例 |
|------|---------|------|
| **硬规则** | 微信阅读习惯、合规要求、教学场景必需的规则 | 字数截断（微信阅读习惯）、问句结尾（教学场景）、步骤限制（教学场景）、术语解释（教学场景） |
| **软规则** | 风格偏好、非强制性的格式要求 | emoji 使用、链接格式、语气风格 |

### 6.5.2 工具实现

- **硬规则**：代码层强制执行（硬规则执行器），无法被 Prompt 绕过
- **软规则**：Prompt 层引导（在人设 Prompt 中描述），LLM 可能不遵守

### 6.5.3 用户配置界面

- 硬规则配置器：明确标注"⚠️ 硬规则由代码层强制执行，无法被 Prompt 绕过"
- 软规则在入设编辑器的"风格指南"段配置
