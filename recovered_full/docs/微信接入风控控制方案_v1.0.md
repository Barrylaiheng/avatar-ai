# 阿凡达 AI · 微信接入风控控制方案

> **文档版本**：v1.0
> **创建日期**：2026-08-29
> **适用版本**：阿凡达 AI v3.x（WCF 渠道）
> **设计依据**：微信风控七层架构技术调研 + 3 个月实际运行数据

---

## 一、方案总览

### 1.1 背景

阿凡达 AI 目前通过 WCF（WeChatFerry）直接注入模式接入微信，已稳定运行 3 个月，日均发送 2 条定时消息，未触发任何风控警告。

随着后续逐步开放多用户、多群的 AI 对话能力，发送量必然上升。需要一套系统化的风控控制方案，在保证用户体验的前提下，最大限度降低被微信风控识别的概率。

### 1.2 设计原则

| 原则 | 说明 |
|------|------|
| **纵深防御** | 不依赖单一手段，多层防护叠加 |
| **默认保守** | 默认参数取经验值的 60-70%，留足安全余量 |
| **可观测** | 所有指标可监控、可统计、可追溯 |
| **可降级** | 支持动态调整档位，检测到风险自动降速 |
| **渐进放量** | 分阶段逐步提升量级，每阶段观察至少 1-2 周 |

### 1.3 四层防护架构

```
┌─────────────────────────────────────────────────────┐
│  第 4 层 · 健康度监控层  AccountHealthMonitor         │
│  （异常信号采集 · 健康评分 · 自动降速 · 预警）        │
├─────────────────────────────────────────────────────┤
│  第 3 层 · 发送队列层  SendQueueController            │
│  （串行发送 · 优先级队列 · 发送间隔模拟 · 回调）      │
├─────────────────────────────────────────────────────┤
│  第 2 层 · 行为模拟层  BehaviorSimulator              │
│  （回复延迟 · 时段因子 · 对数正态分布 · 忙碌概率）    │
├─────────────────────────────────────────────────────┤
│  第 1 层 · 速率控制层  RateController                 │
│  （令牌桶 · 滑动窗口 · 日配额 · 三重限流）            │
└─────────────────────────────────────────────────────┘
```

## 二、第 1 层 · 速率控制层（RateController）

### 2.1 三重限流机制

| 限流方式 | 时间粒度 | 作用 | 默认值（保守档） |
|---------|---------|------|-----------------|
| 令牌桶 | 秒/分钟级 | 防止短时间突发 | 25 条/分钟 |
| 滑动窗口 | 小时级 | 控制小时总量 | 100 条/小时 |
| 日配额 | 天级 | 控制每日总量 | 200 条/天 |

### 2.2 预设档位

| 档位 | 分钟速率 | 小时限额 | 日限额 | 适用场景 |
|------|---------|---------|--------|---------|
| ultra_safe | 10 条 | 30 条 | 50 条 | 新号测试期 / 风险高时 |
| conservative | 25 条 | 100 条 | 200 条 | **默认**，小范围运营 |
| balanced | 40 条 | 200 条 | 350 条 | 稳定运营期（老号） |
| aggressive | 60 条 | 350 条 | 500 条 | 不推荐，仅高权重老号 |

### 2.3 设计要点

- **令牌桶允许一定突发**：桶容量 = 速率 × 0.5，允许短时间内有一定"爆发"，更像真人
- **滑动窗口精确控制**：记录每条消息的时间戳，超出1小时窗口的自动淘汰
- **日配额按自然日重置**：每天 00:00 自动清零
- **失败归还机制**：发送失败时归还日配额，不浪费限额
- **线程安全**：所有操作都有锁保护，支持多线程并发

## 三、第 2 层 · 行为模拟层（BehaviorSimulator）

### 3.1 核心能力

| 能力 | 说明 | 技术实现 |
|------|------|---------|
| 回复延迟模拟 | 收到消息后不是秒回，而是等"阅读+思考+打字"时间 | 对数正态分布 + 长度因子 |
| 发送间隔模拟 | 两条消息之间的间隔（同对话/不同对话不同策略） | 均匀分布 + 抖动 |
| 时段活跃度调整 | 不同时段回复速度不同（深夜最慢、晚间最快） | 24小时因子表 |
| 消息长度关联 | 越长的消息"打字"越久 | 长度因子线性叠加 |
| 忙碌概率 | 偶尔"在忙没看到"，延迟加倍 | 15%概率 × 2.5倍 |
| 漏回模拟 | 偶尔"忘了回"，过很久才回 | 深夜80% / 工作时间10% |

### 3.2 时段因子表

| 时段 | 倍率 | 说明 |
|------|------|------|
| 0:00-5:00 | 6x~12x | 深夜睡觉，回复极慢 |
| 6:00-8:00 | 2x~3x | 刚起床，回复慢 |
| 9:00-11:00 | 0.9x~1.0x | 工作时间，正常速度 |
| 12:00-13:00 | 1.3x~1.5x | 午饭时间，稍慢 |
| 14:00-17:00 | 0.9x~1.0x | 下午工作 |
| 18:00-19:00 | 1.1x~1.2x | 下班路上 |
| 20:00-22:00 | 0.7x~0.8x | 晚间高峰，回复最快 |
| 23:00 | 1.5x | 准备睡觉 |

### 3.3 为什么用对数正态分布？

真人的回复延迟不是正态分布，而是**对数正态分布**——
- 有明显的峰值（大部分在几十秒内回复）
- 有长长的右尾（有时候过了很久才回）
- 这是因为人类行为的"等待时间"普遍符合这个分布

### 3.4 行为模拟档位

| 档位 | 基础延迟中位数 | 拟人程度 | 适用场景 |
|------|--------------|---------|---------|
| ultra_safe | 45 秒 | 最高 | 新号 / 高风险期 |
| conservative | 25 秒 | 高 | **默认** |
| balanced | 15 秒 | 中 | 稳定期 |
| fast | 5 秒 | 低 | 低风险 / 内部测试 |

## 四、第 3 层 · 发送队列层（SendQueueController）

### 4.1 核心作用

把"谁来发消息"这件事从**多线程并发**变成**单线程串行**，加上速率控制和行为模拟。

**为什么不能并发发？**
- 程序并发发消息的话，发送间隔可能只有几毫秒
- 真人不可能同时跟好几个人说话还秒回
- 微信风控的行为时序层（LSTM）会立刻识别出这种模式

### 4.2 队列特性

| 特性 | 说明 |
|------|------|
| 优先队列 | 支持 4 级优先级（低/普通/高/紧急），紧急消息可插队 |
| 串行发送 | 单线程逐条消费，保证发送间隔 |
| 回复延迟 | 回复消息自动加上"思考+打字"延迟 |
| 发送间隔 | 与上一条发送之间自动计算间隔 |
| 速率检查 | 发送前先过 RateController，超限等待重试 |
| 回调通知 | 发送成功/失败都有回调 |
| 可观测 | 队列长度、发送数、失败数、平均等待时间 |

### 4.3 优先级定义

| 优先级 | 用途 | 示例 |
|--------|------|------|
| CRITICAL | 系统消息、安全警告 | 账号异常预警、合规拦截通知 |
| HIGH | 主人指令、紧急回复 | 主人发的消息、安全问题回复 |
| NORMAL | 普通对话回复 | 正常的 AI 对话回复（默认） |
| LOW | 定时推送、通知 | 每日早报、批量通知 |

### 4.4 单条消息处理流程

```
从队列取出任务
    ↓
是回复消息？ ──是──→ 加回复延迟（对数正态 + 时段因子 + 长度因子）
    ↓
计算与上一条发送的间隔
    ↓
间隔不够？ ──是──→ 等待（模拟切换对话/打字时间）
    ↓
速率检查（令牌桶 + 小时窗口 + 日配额）
    ↓
超限？ ──是──→ 等待重试（最多60秒）
    ↓
实际调用 wcf.send_text()
    ↓
记录统计 + 回调
```

## 五、第 4 层 · 健康度监控层（AccountHealthMonitor）

### 5.1 设计理念

微信风控不是"突然死亡"，而是有渐进过程的。健康度监控的目标就是**在最早阶段发现异常信号，自动调整策略，避免走到封号那一步**。

### 5.2 健康度分级

| 等级 | 分值 | 状态 | 建议操作 | 自动降速比例 |
|------|------|------|---------|-------------|
| 🟢 HEALTHY | 80-100 | 健康 | 正常运营 | 0% |
| 🟡 CAUTION | 60-80 | 注意 | 降低频率 30% | 30% |
| 🟠 WARNING | 40-60 | 警告 | 降低频率 60%，停止加好友 | 60% |
| 🔴 DANGER | 20-40 | 危险 | 只被动回复，停止所有主动操作 | 85% |
| 💀 CRITICAL | 0-20 | 紧急 | 完全停止，养号恢复 | 100% |

### 5.3 异常信号分类

| 严重度 | 信号类型 | 扣分 | 衰减时间 |
|--------|---------|------|---------|
| 🟢 低 | 消息发送失败 | 3 分 | 24 小时 |
| 🟢 低 | 加好友无响应 | 2 分 | 12 小时 |
| 🟢 低 | 消息响应变慢 | 3 分 | 6 小时 |
| 🟡 中 | 好友通过率低（<40%） | 8 分 | 48 小时 |
| 🟡 中 | 消息被拒收 | 5 分 | 24 小时 |
| 🟡 中 | 加好友功能受限 | 15 分 | 72 小时 |
| 🟡 中 | 群消息被屏蔽 | 10 分 | 48 小时 |
| 🔴 高 | "操作过于频繁"提示 | 20 分 | 72 小时 |
| 🔴 高 | 朋友圈功能限制 | 25 分 | 120 小时 |
| 🔴 高 | 登录需要额外验证 | 20 分 | 96 小时 |
| 💀 致命 | 临时封禁 | 40 分 | 240 小时 |
| 💀 致命 | 被大量举报 | 35 分 | 168 小时 |
| 💀 致命 | 永久封禁 | 99 分 | — |

### 5.4 自动降速联动

健康度监控器可以和发送队列联动——当健康分下降时，自动降低发送速率档位：

```
健康分 80+ → conservative 档（默认）
健康分 60-80 → conservative × 0.7 降速
健康分 40-60 → ultra_safe 档
健康分 <40 → ultra_safe × 0.5 降速
健康分 <20 → 停止所有主动发送
```

### 5.5 正向恢复机制

不只有扣分，也有加分：
- 正常双向互动 +1 分/天
- 正常登录使用 +1 分/天
- 持续无异常信号，每天自然恢复（衰减的逆向过程）

## 六、与现有架构的集成方案

### 6.1 集成位置

```
现有架构：
    WcfAdapter 收到消息 → MessageRouter → MessageProcessor → 直接 send_text()

集成后：
    WcfAdapter 收到消息 → MessageRouter → MessageProcessor
                                              ↓
                                    SendQueueController
                                          ↓
                              RateController ✓
                              BehaviorSimulator ✓
                              AccountHealthMonitor ✓
                                          ↓
                                    WcfAdapter.send_text()
```

### 6.2 关键改动点

| 模块 | 改动 | 影响 |
|------|------|------|
| AppEngine | 新增 send_queue 实例初始化 | 低 |
| WcfAdapter | send_message 改为调用 send_queue.enqueue() | 中 |
| ConfigManager | 新增风控配置段（rate_profile / behavior_profile / health_auto_adjust） | 低 |
| UI 层 | 新增"风控状态"面板（可选，展示健康度和统计） | 低 |

### 6.3 集成步骤（建议）

**Step 1**：先只接 RateController（最小改动，验证效果）
- 在 WcfAdapter 的 send_text 前加速率检查
- 超限则等待或返回失败
- 预计改动量：~30 行代码

**Step 2**：接入 SendQueueController + BehaviorSimulator
- 所有发送走队列
- 加上回复延迟和发送间隔模拟
- 预计改动量：~100 行代码

**Step 3**：接入 AccountHealthMonitor
- 采集异常信号（发送失败、功能限制等）
- 自动降速联动
- 健康度 UI 展示
- 预计改动量：~150 行代码

## 九、关键假设与局限性

1. **所有阈值基于社区经验**：微信官方不公开具体算法，参数是从逆向分析和社区经验中总结的，可能随时变化
2. **行为模拟是"降低概率"不是"保证安全"**：只能降低被识别的概率，不能完全消除风险
3. **内容安全同样重要**：本方案只覆盖行为和频率层面，内容层面的合规（敏感词、营销话术等）由 SafetyShield v2 负责
4. **社交图谱层面最难模拟**：好友质量、互动率、关系网络密度这些慢变量，需要时间积累，无法通过技术手段快速提升
5. **微信风控持续进化**：今天有效的策略明天可能失效，需要持续观察和调整

## 十、下一步建议

1. **立即实施 Step 1**：先接 RateController，最小改动，先把"发送频率"这个最大的风险点管住
2. **一周后实施 Step 2**：接 SendQueueController + BehaviorSimulator，开始放量到阶段 1（5-10 人测试）
3. **同时开启健康度监控**：即使现在信号很少，先把监控架起来，建立基线数据
4. **每 2 周做一次复盘**：看健康度趋势、发送量、失败率，决定是否进入下一阶段
