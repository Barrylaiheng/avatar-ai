`wecom-aibot-python-sdk` 基于 `wss://openws.work.weixin.qq.com` WebSocket 长连接：

## 二、各渠道接入细节

### 2.1 公众号（微信开发者平台官方文档深度调研）

#### 文档结构（重大变更）

微信已将原"公众号"文档拆分为两个独立体系：

| 文档 | 原名 | 定位 | 消息格式 | 文档地址 |
|------|------|------|---------|---------|
| **公众号** | 订阅号 | 媒体/个人传播 | 仅 XML | https://developers.weixin.qq.com/doc/subscription/guide/ |
| **服务号** | 服务号 | 企业业务服务 | XML/JSON | https://developers.weixin.qq.com/doc/service/guide/ |

**MVP 应接入"公众号"（订阅号）**，因为：
- 订阅号面向个人/媒体，适合 AI 分身场景
- 服务号需要企业资质认证

#### 可用 SDK / 框架

| 方案 | Stars | 说明 | 适合场景 |
|------|-------|------|---------|
| **wechatpy** | 4.3k | 最成熟的 Python SDK，支持被动响应+主动调用+加解密+AccessToken管理 | 推荐，功能完整 |
| **WeRoBot** | - | 轻量框架，内置 Web 服务器，3 行代码搭机器人 | 快速原型 |
| **chatgpt-on-wechat** | - | 参考其 `channel/wewechatmp/` 实现 | 架构参考 |
| **直接 HTTP API** | - | 用 requests 调官方 API | 最小依赖 |

**推荐：wechatpy**（4.3k stars，2026年5月仍在更新）

#### wechatpy 核心能力

- 被动消息响应（文本/图片/语音/视频/事件）
- 主动调用 API（客服消息/模板消息/用户信息/素材管理）
- 消息加解密（明文/兼容/安全三种模式）
- AccessToken 自动刷新 + 持久化存储（Redis/Memory/自定义）
- 签名验证

#### 消息交互链路（官方文档详细版）

```
用户在公众号发消息
    ↓
微信服务器 POST 到回调 URL（必须 80 或 443 端口）
    ↓
MVP HTTP 服务收到请求 → 5 秒内必须响应
    ├── 方式1：被动回复（直接返回 XML）← 5秒限制，不适合 AI
    ├── 方式2：立即返回 "success" + 异步用客服消息 API 回复 ← 推荐
    └── 方式3：返回 transfer_biz_ai_ivr ← 微信自家 AI，不适合我们
```

**消息接收验证流程**（微信服务器验证回调 URL）：
1. 微信发送 GET 请求，携带 signature、timestamp、nonce、echostr
2. 将 token、timestamp、nonce 字典序排序 → sha1 加密 → 与 signature 比对
3. 验证通过 → 原样返回 echostr → 接入生效

**消息重试机制**：
- 微信服务器 5 秒内未收到响应 → 断开连接 → 重试，共 3 次
- 消息排重：有 msgid 的用 msgid，事件类用 FromUserName + CreateTime

#### 安全配置（4 项必配）

| 配置项 | 说明 | 位置 |
|--------|------|------|
| **URL** | 回调地址，必须 http:// 或 https://，仅支持 80/443 端口 | 微信开发者平台 → 公众号 → 消息与事件推送 |
| **Token** | 签名验证令牌，自定义 | 同上 |
| **EncodingAESKey** | 消息加解密密钥，手动填写或随机生成 | 同上 |
| **IP 白名单** | 调用 API 的服务器 IP，否则报 61004 错误 | 微信开发者平台 → 公众号 → 开发密钥 |

**消息加解密模式**（三选一）：
- 明文模式：不加密，安全系数低，不推荐
- 兼容模式：明文+密文共存，不推荐
- **安全模式**：纯密文，强烈推荐

#### Access Token 管理

- 有效期 **2 小时**（7200秒），需定时刷新
- 推荐使用 `getStableAccessToken` 稳定版接口
- 重复获取会导致旧 token 失效
- 刷新期间新老 token 5 分钟内都可用
- 建议中控服务统一获取刷新，其他服务从中控取
- 存储：至少保留 512 字符空间

**MVP 实现**：内置定时器（建议 1 小时刷新一次），存入 SQLite。

#### API 调用额度（关键限制）

| 接口 | 每日限额 | 对 MVP 的影响 |
|------|---------|--------------|
| 获取 access_token | 2,000 | 足够（1 小时刷 1 次 = 24 次/日） |
| **获取关注者列表** | **500** | ⚠️ 很少！必须本地缓存，不能频繁拉取 |
| 获取用户基本信息 | 5,000,000 | 足够 |
| **发送客服消息** | **500,000** | 足够 |
| 获取带参数二维码 | 100,000 | 足够 |
| 上传多媒体文件 | 100,000 | 足够 |

**关键限制**：关注者列表每日只能拉 500 次，必须在本地缓存粉丝列表。

#### 客服消息回复模式（异步回复）

因 AI 处理通常超过 5 秒，必须用异步模式：

```
1. 收到用户消息 → 立即返回 "success"（满足 5 秒限制）
2. 消息进入 ChannelMessage pipeline
3. AI 处理（智能体 + 知识库 + 记忆，可能 10-30 秒）
4. 通过客服消息 API 异步发送回复
   POST https://api.weixin.qq.com/cgi-bin/message/custom/send?access_token=xxx
   { "touser": "openid", "msgtype": "text", "text": { "content": "回复内容" } }
```

**限制**：客服消息只能发给 **48 小时内有互动** 的用户。

#### 微信云托管方案（新发现，备选）

微信官方提供 [云托管](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloudrun/src/guide/weixin/push.html) 方案：
- 免鉴权调用微信接口（无需维护 access_token）
- 无需配置 IP 白名单
- 无需加解密和签名（走内网链路）
- 消息直接推送到云托管服务

**但消息仍然推送到你的云托管服务**，仍然需要公网部署。适合有云开发能力的用户，不适合 MVP 本地化场景。

#### MVP 部署模式

| 方案 | 架构 | 适用场景 | 复杂度 | 用户域名利用 |
|------|------|---------|--------|------------|
| **A. 内嵌 HTTP + 内网穿透** | MVP 内嵌 Flask，配 ngrok/cpolar/钉钉 pierced | 个人/小团队，无服务器 | ⭐⭐ | 域名绑定穿透工具 |
| **A1. 域名 + 内网穿透（固定域名）** | 穿透工具绑定自有域名 | 有域名的用户（推荐） | ⭐⭐ | ✅ 充分利用 |
| **A2. 域名 + DDNS + 端口映射** | 域名指向家宽公网 IP | 有公网 IP 的家宽 | ⭐⭐ | ✅ 充分利用 |
| **B. 独立服务器 + SSH 管理** | 回调跑云服务器，MVP 通过 SSH 管理 | 有服务器的用户 | ⭐⭐⭐ | 域名解析到服务器 |
| **C. 微信云托管** | 微信官方云托管中转 | 有云开发能力 | ⭐⭐⭐ | 不需要自有域名 |

**推荐方案 A1**：用户已有域名 + 内网穿透付费版（如 cpolar/natapp，约 10 元/月），域名固定，不用每次改微信后台配置。

**钉钉官方提供 `pierced` 内网穿透工具**（2.3k stars），可直接用于公众号回调。

#### 关键限制汇总

| 限制项 | 说明 | MVP 应对策略 |
|--------|------|------------|
| 5 秒超时 | 被动回复需 5 秒内响应 | 立即返回 success + 异步客服消息回复 |
| 48 小时窗口 | 客服消息只能发 48h 内互动用户 | 正常对话场景天然满足 |
| 80/443 端口 | 回调 URL 仅支持 80/443 | 内网穿透工具默认支持 |
| 粉丝列表 500次/日 | 获取关注者列表受限 | 本地缓存 + 定时同步 |
| 无群聊 | 公众号不支持群聊 | 前端绑定页隐藏群聊 Tab |
| 无历史消息 | 公众号不提供历史消息 API | 历史记录只记本地 AI 对话 |
| Access Token 2h 过期 | 需定时刷新 | MVP 内置定时器 1 小时刷新 |
| IP 白名单 | 调 API 的 IP 需白名单 | 内网穿透的固定 IP 加入白名单 |
| 消息重试 | 微信会重试 3 次 | 用 msgid 去重 |

**所需参数**：AppID、AppSecret、Token、EncodingAESKey

### 2.2 企业微信

**交互链路（本地 Hook 方案，类 WCF）**：
```
用户 → 企微客户端 → [Hook DLL] → MVP
MVP → [Hook DLL] → 企微客户端 → 用户
```

**交互链路（官方 API 方案）**：

### 2.3 飞书

**交互链路（WebSocket 长连接）**：
```
用户 → 飞书服务器 → [WebSocket 推送] → MVP（本地）
MVP → [API 调用] → 飞书服务器 → 用户
```

**所需参数**：App ID、App Secret

**SDK**：`lark-oapi`（Python），支持 WebSocket 接收事件

**关键优势**：
- 无需公网 IP，本地直接运行
- 官方文档完善，SDK 成熟
- 支持私聊 + 群聊 @机器人

### 2.4 钉钉

**交互链路（Stream 长连接）**：
```
用户 → 钉钉服务器 → [Stream WebSocket] → MVP（本地）
MVP → [API 调用] → 钉钉服务器 → 用户
```

**所需参数**：Client ID（AppKey）、Client Secret（AppSecret）

**SDK**：`dingtalk-stream`（Python），Stream 模式

> **注意：实际实现已偏离本节调研。** MVP 最终未采用 `dingtalk-stream` SDK / Stream 长连接，
> 而是与企微、飞书保持一致，走 **dws CLI 的 user 身份定时轮询**：收消息 `chat message list`、
> 发消息 `chat message send`，凭据 `~/.dws/identity.json`。
> 原因是产品定位为“以用户本人身份通信”，而 Stream 模式只能以机器人身份收消息。
> 故本节及下文的钉钉 Stream 复杂度/链路描述仅作方案调研留档，不代表现状。

**关键优势**：
- 无需公网 IP，本地直接运行
- Stream 模式自动重连
- 支持流式 AI 卡片回复

## 四、架构复杂度分析（修正版）

### 4.1 两种部署模式

**模式 1：全本地（微信、企微、飞书、钉钉）**
```
┌─────────────────────────────────────┐
│           MVP（本地桌面应用）            │
│                                     │
│  ┌─────────────────────────────┐    │
│  │    ChannelClient 抽象层       │    │
│  └──────────┬──────────────────┘    │
│             │                        │
│  ┌──────────┼──────────┬─────────┐  │
│  ▼          ▼          ▼         ▼  │
│ 微信 WCF  企微 WS   飞书 WS   钉钉 Stream│
│ (本地)    (本地)    (本地)     (本地) │
└─────────────────────────────────────┘
```
- 4 个渠道全部本地运行
- 无需公网 IP
- 数据全本地

**模式 2：公网回调（仅公众号）**
```
┌──────────────────────────────┐
│  MVP（本地）                   │
│  └─ 公众号 Client              │
│     ├─ 内嵌 HTTP + 内网穿透     │
│     └─ 或 独立服务器 + SSH 管理 │
└──────────────────────────────┘
```
- 只有公众号需要公网
- 两种子方案可选

### 4.2 结论：架构大幅简化

**之前的担忧（需公网回调）只适用于公众号。** 企微、飞书、钉钉都可以像微信一样在 MVP 本地直接运行，通过 WebSocket 长连接接收消息。

这意味着：
- ✅ MVP 可以统一管理 4/5 个渠道（微信、企微、飞书、钉钉）
- ✅ 不需要为每个渠道配公网服务器
- ✅ 数据全部本地存储，符合隐私需求
- ⚠️ 只有公众号需要额外处理公网回调

### 4.3 MVP 与服务器的关系

| 渠道 | MVP 直接控制 | 通过服务器中转 |
|------|-------------|--------------|
| 微信 WCF | ✅ 必须本地 | ❌ |
| 企微 WebSocket | ✅ 本地即可 | ❌ |
| 飞书 WebSocket | ✅ 本地即可 | ❌ |
| 钉钉 Stream | ✅ 本地即可 | ❌ |
| 公众号 | ⚠️ 需公网 | 可选（内嵌 HTTP 或独立服务器） |

**4/5 渠道 MVP 直接本地控制，只有公众号需要考虑服务器。**

## 六、推荐推进顺序

基于接入难度和功能完整性：

```
第1步：抽象层（~170 行）
  ├─ ChannelMessage + ChannelClient
  ├─ WCF 适配
  └─ Pipeline 泛型化
  ↓
第2步：飞书（~470 行）—— 最简单，WebSocket 无需公网
  ↓
第3步：钉钉（~420 行）—— 类似飞书，复用模式
  ↓
第4步：企微（~470 行）—— 取决于用户选 Hook 还是 API
  ↓
第5步：公众号（~550 行）—— 最复杂，需公网回调
```

**理由**：
1. 飞书/钉钉最简单（WebSocket，无需公网，官方 SDK 成熟）
2. 企微方案取决于用户偏好（Hook 类 WCF 或官方 API）
3. 公众号最复杂（需公网回调，功能受限）

## 七、关键风险与决策点

### 7.1 公众号的公网回调问题

这是最大的架构决策点：
- **方案 A**：MVP 内嵌 HTTP + 内网穿透（适合个人/小团队）
- **方案 B**：独立服务器部署 + MVP SSH 管理（适合企业）
- **方案 C**：MVP 通过 API 调用云端回调服务（适合 SaaS）

### 7.2 功能不对等

公众号无群聊、无历史消息拉取、主动消息受限。智能体功能需要按渠道适配：
- 绑定联系人：公众号是"关注者"，不是"好友"
- 历史消息：公众号只能用 MVP 本地存储的对话记录
- 群聊：公众号不支持

### 7.3 风控策略差异

| 渠道 | 风控需求 |
|------|---------|
| 微信 | 账号风控（防封号）—— 已有完整实现 |
| 企微（Hook） | 中风险，需行为模拟 |
| 公众号/企微 API/飞书/钉钉 | 低风险，只需 QPS 限制 |

## 八、结论（v4）

### 8.1 核心结论

**所有渠道都可以统一在同一个 MVP 里，不需要分开开发。**

4/5 渠道（微信、企微、飞书、钉钉）全部本地运行，只有公众号需要公网回调。

### 8.2 公众号特殊处理（v4 补充）

公众号是所有渠道中最特殊的，需要专门适配：

| 特殊点 | 说明 | 解决方案 |
|--------|------|---------|
| 唯一需公网回调 | HTTP POST 到 80/443 端口 | 域名 + 内网穿透（方案 A1） |
| 5 秒超时限制 | 被动回复必须 5 秒内响应 | 立即返回 success + 异步客服消息 |
| 粉丝列表受限 | 500 次/日 | 本地缓存 + 定时同步 |
| 无群聊 | 公众号不支持 | 前端隐藏群聊 Tab |
| 无历史消息 | 不提供 API | 历史记录只记本地 AI 对话 |
| Access Token 管理 | 2h 过期 + IP 白名单 | MVP 内置定时器 + 白名单配置 |
| 消息去重 | 微信重试 3 次 | msgid 去重 |
| 安全配置 | 4 项必配 | URL + Token + AESKey + IP 白名单 |

**这些差异都被 ChannelClient 抽象层屏蔽**，pipeline 只管处理 `ChannelMessage`。

### 8.3 统一架构

```
同一个 MVP 代码库
├── app/channel/
│   ├── base.py              ← ChannelClient 抽象接口
│   ├── wcf_client.py        ← 微信（本地 Hook）
│   ├── wecom_client.py      ← 企微（WebSocket SDK）
│   ├── feishu_client.py     ← 飞书（WebSocket SDK）
│   ├── dingtalk_client.py   ← 钉钉（dws CLI 轮询，非 Stream SDK）
│   ├── oa_client.py         ← 公众号（HTTP 回调，需公网）
│   └── message_pipeline.py  ← 统一消息处理
└── 前端连接管理页 ← 统一配置所有渠道
```

### 8.4 复杂度总结

| 维度 | 评估 |
|------|------|
| 代码量 | 抽象层 ~170 行 + 每渠道 ~400-550 行 |
| 部署 | 4/5 渠道本地运行，仅公众号需公网 |
| 数据 | 全部本地 SQLite，隐私安全 |
| 风控 | 微信需完整风控，其他渠道只需 QPS 限制 |
| 功能 | 公众号能力最弱（无群聊/历史），其他基本对齐 |

### 8.5 推荐推进顺序

```
第1步：抽象层（~170 行）
  ├─ ChannelMessage + ChannelClient
  ├─ WCF 适配
  └─ Pipeline 泛型化
  ↓
第2步：企微（~470 行）—— 有官方 Python SDK，和微信生态近
  ↓
第3步：飞书（~470 行）—— 官方 SDK 成熟，WebSocket
  ↓
第4步：钉钉（~420 行）—— Stream 模式，类似飞书（实际实现改为 dws CLI 轮询）
  ↓
第5步：公众号（~550 行）—— 需公网回调，最后做
```
