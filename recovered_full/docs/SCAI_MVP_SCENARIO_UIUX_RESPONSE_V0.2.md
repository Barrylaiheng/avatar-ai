## MISS-07 · AIGC 盖章文案（P1 最急 · 已从源码提取 + 合规要求）

**来源**：`src/aibridge/engine/aigc_marker.py` + 项目记忆"AIGC content must have mandatory identification in compliance with July 15 regulations"

### 当前实现状态

代码中有两个盖章器：

| 类名 | 机制 | 当前状态 | 实际效果 |
|------|------|---------|---------|
| `AigcImplicitMarker` | 隐式标记：在消息 metadata 中加 `is_aigc: true` | **默认启用** | 用户不可见，仅机器可读 |
| `AigcExplicitLabeler` | 显式标记：在消息内容前加 prefix / 后加 suffix | **默认关闭** | prefix 默认值 `"[AI生成]"`，suffix 默认空 |

### 三个版本的盖章文案（⚠️ 需用户确认最终文案）

根据 2025 年 7 月 15 日《人工智能生成合成内容标识办法》要求，建议三档：

| 版本 | 字数限制 | 适用场景 | 建议文案 |
|------|---------|---------|---------|
| 短版 | ≤20字 | 微信单条回复（字数敏感） | `[本消息由AI分身生成]` |
| 标准版 | ≤60字 | 邮件/长回复 | `[本消息由AI分身生成，如有疑问请联系本人]` |
| 长版 | ≤150字 | 公众号/正式回复 | `[本消息由影分身AI辅助生成。根据《人工智能生成合成内容标识办法》要求，特此标识。内容仅供参考，最终解释权归本人所有。]` |

⚠️ **需用户确认**：
1. 上述文案是否合规？是否需要法务审核？
2. 微信场景用短版还是标准版？
3. 是否所有回复都盖章，还是只有超过一定字数的回复才盖章？
4. prefix 方式（加在消息开头）还是 suffix 方式（加在消息末尾）？当前代码默认是 prefix。

## §2.1 WCF 16 场景补充说明

以下为 UI/UX 侧对每个场景的补充，基于 ui_mockup.html 设计意图和项目记忆中的约束。

| 场景 | UI/UX 补充说明 |
|------|---------------|
| WCF-01 纯文字私聊 | 处理模式正确。补充：回复后在工作台留"待办"记录，主人可查看/撤销/重新编辑 |
| WCF-02 纯文字群聊@主人 | 补充：群里回复必须@回那个人（社交礼仪），这是硬性要求 |
| WCF-03 群里没@你的消息 | UI/UX 设计意图：**默认不处理**。只有"群设置里标了重点群"才扫描，发现关键字提醒主人。MVP 阶段可以先不做重点群扫描 |
| WCF-04 图片消息 | MVP 不处理。弹 Toast"XX发来图片，请亲自查看"。不接 OCR |
| WCF-05 语音消息 | MVP 不处理。弹 Toast"XX发来语音，请亲自收听"。不接语音转文字 |
| WCF-06 表情包 | MVP 不回复。忽略，不弹通知。理由：表情包无需回复，回复反而奇怪 |
| WCF-07 视频/文件/PDF | MVP 不处理。弹 Toast"XX发来文件：文件名，请查看"。不接文件解析 |
| WCF-08 转账/红包/名片 | **硬性规则**：一律转主人亲自处理，AI 绝不碰。弹红色 Toast 加急提醒 |
| WCF-09 位置/小程序/视频号 | MVP 不处理。弹 Toast"XX发来位置/链接，请查看" |
| WCF-10 微信电话 | MVP 不处理。弹 Toast"XX正在呼叫你"。AI 不能接电话 |
| WCF-11 空消息/纯链接 | 安全先扫链接→如果是钓鱼/恶意链接，记录但不回复；如果正常链接，转主人"XX发来链接，请查看" |
| WCF-12 刷屏/重复消息 | UI/UX 设计意图：10秒内同一人发5条以上 → 只处理最后一条，前面作废。不弹限流提示给用户（静默处理） |
| WCF-13 消息被撤回 | 作废正在生成的回复。记录撤回事件到档案柜。如果回复已经发出去了 → 无法撤回，记录"对方撤回了消息但AI已回复" |
| WCF-14 主人手动回复 | **必须同步**。主人手动回复的消息要写入档案柜历史记录，这样下次AI回复就知道主人刚才说了什么。这是防止AI风格跳变的关键 |
| WCF-15 好友被删/被踢/被封 | 弹 Toast"微信联系人变更：XX已删除你/你已被移出XX群"。更新联系人缓存 |
| WCF-16 微信掉线 | 弹 Toast"WCF连接断开，请检查微信是否在线"。自动重连最多5次（15秒间隔），超过后停止重连，等主人手动处理 |

| 场景 | 说明 |
|------|------|
| WCF-17 公众号文章分享 | 有人转发公众号文章给你。MVP 不处理，弹 Toast"XX分享了一篇文章" |

## 附录 · 历史业务场景梳理（从项目记忆库提取）

> 以下信息从 2026-08-01 ~ 2026-08-06 的 session memory 和 topics.md 中提取，是当初做 ui_mockup.html 时梳理过但未随 HTML 交付给 code 侧的业务场景背景。

### A1. 产品定位演进（§0.1 补充）

| 时间 | 定位 | 关键决策 |
|------|------|---------|
| v1.0-v3.1 | 数字分身交付工具 | 经历三次形态演进 |
| 2026-08-01 | 核心卖点是 LLM+Prompt+RAG+LLM Wiki+迭代系统的克隆/蒸馏能力，不是 AI 控制微信 | 明确"卖工具"vs"卖服务"的定位摇摆 |
| 2026-08-06 | 知识蒸馏工具，不是渠道搭建工具 | 核心卖点 = 数字分身提炼 + 知识库搭建 |

### A2. 业务模型：两段式漏斗（§1 补充）

```
第一层：卖服务（数字分身微信咨询）
  → 公域引流 → 公众号免费体验 → 加微信 → 分档付费
  → MVP 应优先验证这一层

第二层：卖工具/知识（从第一层服务过程中自然产生）
  → 用户买了服务后想自己搭建分身 → 买工具
  → 代码资产集中在这一层，但 MVP 应先验证第一层
```

⚠️ **需用户确认**：当前 MVP 是验证第一层（卖服务）还是第二层（卖工具）？这决定了功能优先级。

### A3. 两条用户路径（§0.1 补充）

| 路径 | 用户行为 | 工具角色 |
|------|---------|---------|
| Path A（仅工具） | 用户用工具蒸馏知识、搭建分身 → 导出文档自行部署 | 工具到此为止，不负责运行环境 |
