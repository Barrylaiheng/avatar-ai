## 0. 前置共识（整场梳理的地基）

| 项 | 结论 |
|---|---|
| MVP 是什么 | **一条「把渠道里的文本接到大模型上」的通道**，不是 AI Agent |
| MVP 核心四件套 | **LLM + Prompt + RAG + Context + 迭代系统** |

| 讨论起点 | **在「连接」部分的开发过程中，发现了文件进出 + 主人身份这两个需求**——不是凭空加的，是连接打通后自然浮出来的 |

## 1. 三角关系：智能体 / 主人 / 用户

| 角色 | 是谁 | 与智能体的关系 |
|---|---|---|
| **主人** | 拥有这个智能体的人（只有一个） | 智能体的**管辖者**——智能体向主人汇报、听主人指挥 |
| **用户** | 主人微信/企微等渠道里的联系人（很多个） | 智能体的**服务对象**——智能体代表主人回他 |
| **智能体** | 以主人语气说话的 AI 分身 | 站在中间的**履约者** |

一句话：**用户，是智能体要「接住」的人；主人，是智能体要「汇报」的人。**

---

## 2. 文件进出

### 2.1 定性：不是手递手，是「前台」

- **手递手**：渠道把字节从 A 搬到 B，中间不拆、不看、不判断。
- **智能体**：**前台**——拆开看、定去向、触发事。

> **送到，是渠道的事；接住，是智能体的事。**

所以文件进来，**不是**原样转给主人，也**不是**替用户把活儿干了（写作类需求 MVP 不解决）；而是**智能体先读懂 → 认下意图 → 产出结论 → 放到该放的人面前**。

### 2.2 方向是双向的

| 方向 | 链路 | 智能体做的事 |
|---|---|---|
| **进** | 用户 → 智能体 → 主人 | 读懂文件、跟用户确认意图、记住、待主人问时给结论 |
| **出** | 主人 → 智能体 → 用户 | 读懂文件、按主人指示提炼、用**语言**讲给用户 |

### 2.3 交互三步模型（用户提出，已校验成立）

> ① **对文件内容做分析** → ② **用户/主人给出明确指令** → ③ **智能体推进下一个动作**

校验结论：**方向成立**，且比"直接分析完就完事"多一步——**②「定意」= 跟人确认**。这一步是关键，没有它智能体就只是"读了个文件"，不构成"接住了一件事"。

### 2.4 下一阶段的目标形态：给智能体加一个「感官」

现有智能体只有一个感官：**文字**。围着旧感官长起来的东西（人设 / 记忆 / 风控 / RAG）都要跟着重新对齐。

文件跟文字不是一个物种：

| | 文字 | 文件 |
|---|---|---|
| 形态 | 说出来的 | **递过来的** |
| 语气 | 自带语气 | 不带，要自己读 |
| 时效 | 说完就过去 | **一件等着被处理的事** |

**目标形态一句话：**

> 智能体把「文件」当作**一份带指令的事**来接：读懂内容 → 认下意图 → 产出结论 → 放到该放的人面前。
> **它的产出物是语言，不是文件。**

### 2.5 三条主线（From → To）

| 主线 | From（现在） | To（下一阶段） |
|---|---|---|
| **输入线** | 只收文字 | 收文件 + 认出来源与提交人 |
| **处理线** | 直接生成回复 | 读懂 → 跟人确认意图 → 产出「结论」 |
| **落点线** | 回给对话对象 | 结论按身份落到该去的地方（主人 / 用户） |

> 优先级判断：**处理线是真正的核心**；落点线必须在处理线之后（没有结论，落点无意义）；输入线目前已在推进。

### 2.6 关键分岔：产出到底是「一句回复」还是「一个结论」

| | 回复 | 结论 |
|---|---|---|
| 给谁 | 对话对象 | 主人 |
| 形态 | 一句对话 | 一条可交付的信息 |
| 生命周期 | 说完就过去 | **要留存、要被查** |

这是文件进出真正要先拍的一刀。

### 2.7 收敛结论（用户已确认）

> **文件进出 = 「提炼」这个动作。** 它和知识库现有的「上传文档」本质是同一件事——只是现在**没做提炼、也没定提炼产物放哪**。所以文件进出不用另立门户，**归到「知识库」这条线**即可，"不用搞得太复杂"。

## 3. 两条数据线的边界

### 3.1 现有事实：两条线互不写入

| 线 | 唯一来源 | 写入方 | 对对方 |
|---|---|---|---|
| **知识库** | **人在知识库页手动上传文档** | `docs_dao.create` + `save_chunks` | 对话/记忆**只读** |
| **记忆与进化** | **对话**（含从会话导入） | `_extract_and_save_memory` | 不写知识库 |

> **知识库边界一句话**：知识库 = **主人亲手放的资料**；只读给智能体查；对话和记忆都不往里写。

### 3.2 后端差异：切片 vs 记忆条目

| | 知识库 | 记忆与进化 |
|---|---|---|
| 存的是 | 文档**切片** | 记忆**条目** |
| 怎么生效 | 被检索命中才出现（**影响它能引用什么**） | 注入提示词，每次对话都带着（**影响它是谁、怎么说话**） |
| 类比 | 书架上的一本书 | 它脑子里记着的事 |

### 3.3 文件进出会打破的那道边界

知识库目前**只有一种来源：人**。文件进出会带来**第二种来源：渠道**。

于是产生一个必须明确的边界问题：

> **渠道进来的文件，算不算「主人维护的知识库内容」？**
> - 算 → 必须能分得清来源（人工上传 vs 渠道进入）
> - 不算 → 单独存，只让查

### 3.4 资料 vs 台账

| | 资料（知识库装得下） | 台账（知识库装不下） |
|---|---|---|
| 内容 | 文件**里的内容** | **谁、在什么时候、交了什么** |
| 例子 | 那份方案写的什么 | 小张今天交了方案这件事 |

> 结论：**文件里的内容归知识库；「事件」先不管。**

### 3.5 遗留硬问题：记忆不分人

现有记忆是**挂在智能体身上的一整份**（`ai_agent.memories`，由会话 merge 回智能体自己），**不按联系人隔离**。

后果：组织场景下，**张三交的东西会串给李四**。这是引入"组织管理协同"后必须面对的一颗雷，本纪要先标记，不在本轮定方案。

## 4. 绑定主人

### 4.1 定性：主人不是「权限」，是「认得人」

讨论中修正过一次口径：用「权限」这个词容易带偏，因为它站在**系统**角度（谁准不准）。而智能体需要的是站在**它自己**角度——**认不认得对面是谁**。

例子：用户问"这个企业里有多少个 X"——不能说；主人问同一句——能说。

### 4.2 这背后是两个机制

| | 机制 | 谁来做 | 决定什么 |
|---|---|---|---|
| ① | **认得人**：知道对面是主人还是用户 | Prompt / 上下文 | 影响它**主动**的言行（口吻、要不要汇报、该不该答） |
| ② | **有的说 / 没的说**：装配上下文时按身份决定塞了什么 | 数据（装配层） | 影响它**客观上**说不说得出来 |

- 只有 ①：用户说句"我是老板"就可能被套话（软认知能被绕）。
- 只有 ②：它不知道自己面对谁，对主人也是客服口吻，该汇报的不汇报。

**两条一起，才成立。**

### 4.3 装配里缺的那一维：「你」

现有 System Prompt 的装配顺序（`app/bridge.py` system_parts）：

| 段 | 内容 | 视角 |
|---|---|---|
| persona | 我是谁、怎么说话 | **我** |
| 固定句 | "请用中文回复，自然、口语化" | **我** |
| memories | 我记得什么 | **我** |
| ANCHOR_RULES | 我的底线规则（所有智能体共享） | **我** |
| kb_context | 我查得到什么（RAG） | **我** |

> **四段全是「我」。缺的正好是「你」——对面是谁。**
> 这不是缺功能，是装配上下文缺了**一个维度**。

补充事实：`peer_id` / `peer_name` 其实一路传到了 bridge（pipeline 装进 payload、bridge 收下），但**只用于建会话和显示历史名字，从未喂给 LLM**。原料在手上，只是没喂进去。

### 4.4 为什么主人规则是「系统性的」

> **它不是挂在某个智能体身上的配置开关，而是「装配上下文」这件事本身多出来的一层。**

- 每个智能体都要经过这套装配 → 天然都有，不用各自配。
- 因此它**不属于角色配置**——用户能填的只有「**谁是我的主人**」（一个身份标识）；「**主人意味着什么**」（认得人、该说什么不该说什么）由系统定，**不给改**。

### 4.5 决定：走「方案 A」——绑定时填标识

| 方案 | 主人在哪 | 怎么认出来 |
|---|---|---|
| **A（采纳）** | 在渠道里（另一个号） | 装配时用 `peer_id` 与主人标识比对 |
| B（保留） | 在桌面端 | 靠"入口"本身 |

**方案 A 落地三件事：**

1. **数据**：主人**不是**通讯录里多加一个人。`channel_binding`（管"哪些人归谁管"）不动；在 `ai_agent` 上多一个**指向**（如 `owner_channel` + `owner_peer_id`），只指向已有联系人里的某一个。
   - 为什么不混进绑定表：一混进去，"主人"和"客户"在数据上就一样了，后面每处按身份分岔都得再猜。分开存，一眼分清"被服务的"还是"发令的"。
2. **装配**：多一个判断——当前 `peer_id` 等于主人标识 → 这一轮的"你" = 主人；否则 = 普通用户。
3. **前端**：**复用现有「联系人列表 + 绑定」界面**（微信 / 企微 / 飞书 / 钉钉各自的联系人列表 + "确认替换绑定"弹窗），只加一个「**标主人**」的动作。— 落地形态见 **6.4「连接与绑定」tab 定稿**。

> 成本判断：**不是新做一个功能，是给已有的绑定界面加一个"标主人"的动作。**

### 4.6 必须说清的口径：本机登录号的消息进不来

客户端层会过滤掉"自己发的"消息（`app/channel/wcf_client.py` 的 `if not msg.is_self`）——这本身是对的（智能体不该回自己主人的话）。

推论：
- 方案 A 认出的"主人"，必然**是另一个号**（本机登录号的好友）。企业场景说得通：**智能体跑在工作号上，老板用自己的号跟它说话。**
- 若"主人"是"**装这个 App、登录这个号的人**"，他发消息在渠道里进不来，得走**桌面端入口**——那是方案 B 的领域。

> 结论：**A 和 B 不冲突，是两个入口。** 建议先做 A（复用现成 UI、成本低），B 等"主人要直接跟智能体对话"时再做。

## 5. 资源类型纪律（总纲）

梳理中反复确立、必须守住的一条：

| 资源类型 | 归哪条线 | 绑定主人后 | 文件进出后 |
|---|---|---|---|
| **Prompt** | 角色 / 主人（"我" + "你"） | ✅ 只动这里 | 不动 |
| **RAG** | 知识库 | ❌ 不动 | ✅ 提炼产物进这里 |
| **Context + 迭代系统** | 记忆与进化 | ❌ 不动 | 不动 |

> **不要混乱，不然系统就很混乱。**

**保存行为**：点「保存配置」→ 提示「✓ 已保存 · 窗口保持打开」，**不关闭弹窗**（现状是 `saveChannelConfig()` 里直接 `closeModal('channelModal')`，这是要改掉的那一处）。

## 7. 结论汇总

### 7.1 已定（本轮收敛）

1. MVP = 把渠道文本接到大模型的通道；核心四件套 = LLM + Prompt + RAG + Context + 迭代系统。
2. 用户/主人/智能体三角：**用户是"接住"的人，主人是"汇报"的人。**
3. **文件进出不是手递手，是智能体做"前台"**；产出物是语言，不是文件。
4. 交互三步模型成立：**内容分析 → 明确指令（定意）→ 推进动作**。
5. 下一阶段目标形态 = **给智能体加一个"感官"**；三条主线中**处理线是核心**。
6. **文件进出 = 提炼动作**，归到「**知识库**」这条线，不另立门户。
7. **知识库边界**：主人亲手放的资料，只读给智能体查；对话和记忆都不往里写。
8. **资源类型纪律**：Prompt = 角色/主人；RAG = 知识库；Context + 迭代 = 记忆与进化。
9. **绑定主人 = 认得人**（两个机制：认得人 + 有的说），不是"给权限"。
10. **主人规则是系统性的**：属于装配上下文的一个维度，不属于角色配置；用户只能指定"谁是主人"。
11. **主人识别走方案 A**（绑定时填标识 + 复用现有联系人 UI）；A/B 两个入口不冲突，先做 A。
12. **主人不做模板**；绑定功能是加法（不改变现有格局）。⚠️ 但闸门口径已变为**收费闸门**，见 6.4。
13. **「连接与绑定」tab 前端定稿**：① 连接渠道**单选、直接排他**（群聊整条不出现）；② 绑定管理者 = 勾选框 + 全选 + 整批生效开关，**挂正式版闸门**。
